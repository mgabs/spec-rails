# pinned-openspec-scaffold Specification

## Purpose
Defines the pinned, CLI-free OpenSpec workflow that `spec-rails init` installs as plain files, and the maintainer path for upgrading the pinned OpenSpec version.

## Requirements

### Requirement: REQ-POS-1 Single Pinned Version
spec-rails MUST record the pinned upstream OpenSpec version in exactly one file (`openspec-version`), and the shipped reference snapshot, skills and scaffold MUST all derive from that version.

#### Scenario: Version is discoverable
- **GIVEN** a checkout of spec-rails
- **WHEN** `openspec-version` is read
- **THEN** it contains one semver string (initially `1.16.0`) and no other file hard-codes an OpenSpec version

### Requirement: REQ-POS-2 CLI-Free Skills
The shipped ports of the `openspec-explore`, `openspec-propose`, `openspec-apply-change`, `openspec-archive-change`, `openspec-sync-specs` and `openspec-update-change` skills MUST NOT instruct the agent to run the `openspec` command and MUST NOT declare `allowed-tools: Bash(openspec:*)`; they MUST read the schema, templates and change directories directly, and none MUST set `user-invocable: false`.

#### Scenario: No openspec invocation
- **GIVEN** the shipped skills
- **WHEN** they are searched for `openspec ` command invocations and `Bash(openspec`
- **THEN** none are found

#### Scenario: Skills are invocable
- **GIVEN** the shipped skills
- **WHEN** their frontmatter is read
- **THEN** none sets `user-invocable: false`

### Requirement: REQ-POS-3 Reference Snapshot
spec-rails MUST commit a pristine copy of the upstream skills and scaffold generated by the pinned OpenSpec version under `vendor/openspec/<version>/`, used only as the diff baseline for upgrades and never copied into target repos.

#### Scenario: Snapshot matches pin
- **GIVEN** `openspec-version` is `1.16.0`
- **WHEN** the snapshot directory is listed
- **THEN** `vendor/openspec/1.16.0/` exists and no other version directory does

### Requirement: REQ-POS-4 Upgrade Script
`scripts/upgrade-openspec.mjs <version>` MUST run the upstream OpenSpec at `<version>` in a temporary directory, replace `vendor/openspec/<old>/` with `vendor/openspec/<version>/`, update `openspec-version`, and print a diff of upstream skill changes versus the previous snapshot so the maintainer can port them to the shipped skills. It MUST NOT modify shipped skills automatically and MUST NOT run from `init`.

#### Scenario: Upgrade to a new version
- **GIVEN** the pinned version is `1.16.0`
- **WHEN** the script runs with `1.17.0`
- **THEN** `openspec-version` reads `1.17.0`, `vendor/openspec/1.17.0/` replaces the old directory, a skill diff is printed, and shipped skills are unchanged

#### Scenario: Re-run is reproducible
- **GIVEN** the script was run with the pinned version
- **WHEN** it runs again with the same version
- **THEN** no file under `vendor/` changes

#### Scenario: Unknown version
- **WHEN** the script runs with a version that cannot be fetched
- **THEN** it exits non-zero and changes no file

### Requirement: REQ-POS-5 Drift Check
A test MUST fail when a skill present in the snapshot has no shipped counterpart, or when a shipped skill lacks the `openspec-version` it was ported from in its frontmatter metadata.

#### Scenario: Missing counterpart
- **GIVEN** the snapshot has a skill with no shipped counterpart and no documented exclusion
- **WHEN** the test suite runs
- **THEN** it fails naming the skill

### Requirement: REQ-POS-6 Bootstrap Through Local OpenSpec
When `openspec/` is absent, `init` MUST bootstrap by running the `openspec` found on `PATH` as `openspec init --tools <list>` (default `agents`), then set `schema: spec-rails` in `openspec/config.yaml`. It MUST fail without writing anything when `openspec` is absent or differs from the pinned major.minor, and MUST NOT execute `openspec` when `openspec/` already exists.

#### Scenario: Empty repo
- **GIVEN** a directory with no `openspec/` and the pinned `openspec` on PATH
- **WHEN** `init --tools agents,github-copilot` runs
- **THEN** `openspec init --tools agents,github-copilot` is executed and `openspec/config.yaml` has `schema: spec-rails`

#### Scenario: Missing or mismatched CLI
- **GIVEN** no `openspec/` and either no `openspec` on PATH or a different major.minor than pinned
- **WHEN** `init` runs
- **THEN** it exits non-zero with a message naming the pinned version and writes nothing

#### Scenario: Day-two run without CLI
- **GIVEN** a repo with `openspec/` and no `openspec` on PATH
- **WHEN** `init` runs
- **THEN** it exits 0 and executes no `openspec` command

### Requirement: NFR-POS-1 No Target Dependency
Files written by `init`, and the skills after the overlay, MUST NOT reference `openspec` or `spec-rails` as an executable, package or dependency, and `init` MUST NOT modify `package.json` or lockfiles.

#### Scenario: Footprint check
- **GIVEN** a repo with a `package.json`
- **WHEN** `init` runs
- **THEN** `package.json` and lockfiles are unchanged and no generated file runs `openspec` or `spec-rails`

### Requirement: REQ-POS-7 Overlay Across Agent Layouts
After bootstrap and on every run, `init` MUST find every OpenSpec-generated skill and command file for the six ported workflows (explore, propose, apply, archive, sync, update) in any agent layout, keep its path and agent-specific frontmatter fields, replace its body with the CLI-free port, and remove `allowed-tools: Bash(openspec:*)` and `user-invocable: false`. Repeating the overlay MUST change nothing.

#### Scenario: Multiple agents
- **GIVEN** a bootstrap with `--tools agents,github-copilot,claude`
- **WHEN** the overlay completes
- **THEN** every generated skill and command for the six workflows in all three layouts has the CLI-free body, retains its original path and name, and contains no `openspec ` command invocation

#### Scenario: Overlay idempotent
- **GIVEN** an overlaid repo
- **WHEN** `init` runs again
- **THEN** no file changes

#### Scenario: Unported workflow
- **GIVEN** a generated workflow (such as onboard) with no port
- **WHEN** the overlay runs
- **THEN** its file is untouched and `init` logs it as still requiring the `openspec` CLI

### Requirement: REQ-POS-8 Upgrade Path
Upgrading OpenSpec MUST consist of: running `scripts/upgrade-openspec.mjs <version>`, porting the printed diff to the shipped skills, and releasing; and for a target repo, running `openspec update` followed by `spec-rails init`. `init` MUST NOT run `openspec update`.

#### Scenario: Target upgrade
- **GIVEN** a target repo updated by `openspec update`, whose generated skills now call the CLI again
- **WHEN** `spec-rails init` runs
- **THEN** the overlay restores the CLI-free bodies
